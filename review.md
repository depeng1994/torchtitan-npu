### Findings

| ID | Severity | Code location | Problem | Impact | Suggested change |
| --- | --- | --- | --- | --- | --- |
| P1-R1 | **P1** | `lora.py: unpack_expert_factors(), _expert_targets(), build_lora_merge_plan(), merge_lora_weight()` | The offline merge plan does not validate the adapter's semantic rank/expert cardinality against the base model. For ordinary dense adapters, the `rank` argument is not checked at all: an A/B pair whose inner rank is internally consistent but differs from `adapter_config.r` still reaches `merge_lora_weight()`, where the matrix shape can be valid and the merge succeeds with the wrong `alpha / r` scaling. For routed experts, `experts = a.shape[0] // rank` is inferred only from the packed adapter. If the supplied rank is wrong but divides `a.shape[0]`, the reshape still succeeds; for split per-expert base checkpoints, the code then emits targets only for `range(experts)`. A base with more experts therefore accepts a shorter inferred prefix and silently leaves the remaining experts unmerged. In the worst case, a wrong rank also re-partitions packed columns/rows across experts while keeping every resulting 2-D delta shape valid. | A malformed/mismatched adapter can produce a checkpoint that loads successfully but contains numerically wrong or only partially merged experts. This is substantially worse than a fail-fast shape error. | Validate every A/B pair against `rank` before building targets: dense LoRA must require `A.shape[0] == B.shape[1] == rank`. For expert adapters, require `A.shape[0] == B.shape[1] == expected_num_experts * rank`. Derive `expected_num_experts` from the split expert keys in `base_weight_map` when available; for fused expert tensors, pass the model expert count into the plan (or validate it when the fused base tensor is loaded) rather than treating the adapter-implied count as authoritative. Also require the discovered per-expert ID set to exactly match the expected contiguous expert set, not merely that every generated prefix target exists. |
| P1-R2 | **P2** | `lora.py: _make_lora_adapter_config_cls().Config.__post_init__()/base_filter` | The TorchAO-NPU composition currently replaces the original `ParamSwapConfig.params_filter_fn` semantics with a DeepSeek-V4 allowlist: only `weight/w1_EFD/w2_EDF/w3_EFD` plus `ndim >= 2` may pass. The needed semantic delta is much smaller: preserve the quantization policy for the base module and exclude LoRA adapter parameters. Because `ParamSwapConfig` recursively supplies parameter FQNs, this can be expressed as a negative adapter filter composed with the original filter. The current allowlist means any future base parameter selected by the original policy is silently not quantized only when LoRA is enabled. | Quantized non-LoRA and quantized-LoRA versions of the same module can drift in base precision semantics after an upstream/repository module change. The hardcoded list also creates a second place that must know every base parameter spelling. | Keep the existing `copy(policy)` (it correctly avoids mutating the shared policy object), but make the wrapper preserve the original predicate and only reject adapter FQNs, e.g. base selection = `original_filter(param, fqn)` AND “not a LoRA adapter parameter”. Do not add an independent `ndim` restriction unless that restriction already belongs to the original quantization policy. This reduces the LoRA/quantization coupling to its actual requirement: adapters stay floating. |
| P1-R3 | **P2** | `lora.py: LoRASelectiveAC`; `parallelize.py: parallelize_deepseek_v4()` | The AC workaround does not compose with the upstream extension mechanism it is built on. TorchTitan v0.3.0 explicitly exposes `SelectiveAC.get_save_ops()` for subclasses, but the activation policy is replaced only when `type(ac_config) is SelectiveAC.Config`. Any legitimate derived SelectiveAC config silently skips the LoRA bmm rule. At the same time, `LoRASelectiveAC.get_save_ops()` removes **all** `aten.bmm` from the save set for every LoRA block, while its comment attributes the need to `Indexer.select`'s in-place ReLU; that Indexer behavior itself is not LoRA-specific. The gating condition and the stated root cause therefore do not line up. | A future/upstream custom SelectiveAC subclass can reintroduce the mutation/recompute hazard without an error, while the default LoRA path pays a broader-than-explained bmm recomputation cost. This is exactly the sort of fragile subclass interaction likely to break on upstream upgrades. | First make the root cause/scope explicit. If the correctness issue is the Indexer in-place mutation, prefer fixing/isolating that mutation or a DSV4-level SAC policy instead of creating a LoRA-only policy. If the rule is genuinely LoRA-specific, make policy composition explicit; at minimum fail fast for an unsupported derived `SelectiveAC.Config` rather than silently bypassing the rule. Do **not** simply broaden the check to `isinstance` and derive into `LoRASelectiveAC.Config`, because that would silently drop fields/semantics owned by the custom subclass. |
| P1-R4 | **P2** | `config_registry.py: _dsv4_muon_profile()/muon_pattern` | LoRA compute layouts are mostly derived from the existing base `shardings` plus `DEEPSEEK_V4_LORA_TARGETS`, but Muon membership is separately re-spelled as a long regex list. Those two decisions can now drift independently. In particular, adding a new LoRA target to `MODULE_PATHS/DEEPSEEK_V4_LORA_TARGETS` can automatically create its LoRA config/export mapping and even its derived compute layout, yet the optimizer regex can omit it; the catch-all AdamW group then accepts it silently, so there is no configuration error. | A later target addition can unexpectedly change optimizer choice from the intended Muon behavior to AdamW with no failure, despite a valid compute layout being present. This duplicates model topology knowledge in exactly the area this PR is trying to centralize. | Establish one source of truth for “LoRA parameters admitted to Muon” and use it for both regex generation and compute-layout generation. Keep only the genuine exception explicit: `w13_lora_b[E,F,2,R]` is intentionally excluded and falls through to AdamW. Add an invariant/assertion that every LoRA parameter matched by the Muon group has a compute layout and every intended Muon LoRA layout is reachable by the Muon pattern. |

## 总体结论

**Overall review: Request Changes.**

The PR direction is coherent — it keeps NPU/model-specific code out of \`patches\`, reuses upstream TorchTitan hooks, centralizes PEFT module mapping, and extends the existing optimizer/checkpoint infrastructure instead of creating a parallel training stack. However, the current change set still has one silent checkpoint-corruption path, incomplete quantized-LoRA verification, fragile AC/quantization/Muon coupling, and avoidable launcher/test complexity. Those must be resolved before approval.

### 4. 遗漏检查与横切结论

最终跨文件复核未发现新的独立 P1/P2 缺陷需要在 21 条之外追加。此前分段容易遗漏的几个横切面重新核对后结论如下：原始 15 个产品文件均围绕 LoRA/Muon/量化/export/test/example/doc，没有无关 patch、PyTorch patch 或 override 混入；非 LoRA 路径仍保持 AdamW 默认、量化 filter 包装只存在于 LoRA 动态 Config，当前普通训练入口没有被直接改变；A5 CPT 的用户 CLI 位于量化默认值之后，因此复用 CPT 本身能保持用户 override 能力；\`MODULE_PATHS\`/state-dict mapping 与 expert pack/unpack 在合法 metadata 下没有发现额外映射错误。也就是说，Final Review 的新增工作是**去重、收窄与严重级别统一**，不是再堆叠新的 finding。

### 5. 最终整体判定

**Request Changes。**

必须修复项精简为六组：

1. **离线 merge 正确性与工具安全**：修 FR-1、FR-5、FR-6、FR-7，确保 rank/专家数不静默错合并、量化输入有可操作错误、内存/输出失败安全，以及 fused expert consumer oracle 真正可运行。
2. **量化 LoRA 闭环**：修 FR-2，删除独立 base allowlist 真源，并补一个真实 TorchAO-NPU LoRA NPU ST；不能以可 skip 的 CPU wrapper test 代替。
3. **Selective AC owner**：修 FR-3，让 bmm recompute policy 跟随真正的 Indexer/DSV4 mutation 语义，而不是 LoRA 条件。
4. **Muon 单一真源**：修 FR-4，让 target membership、compute layout 与测试从同一声明派生，显式保留 \`w13_lora_b\` AdamW 例外。
5. **Resume 进入必跑验证**：修 FR-8，把已有强 snapshot/resume oracle 接入仓库控制的 CI suite，并同步测试文档。
6. **训练入口收敛**：修 FR-9，删除无独立语义的 A5 LoRA wrapper，用现有 A5 CPT + \`CONFIG\`/CLI 暴露同一能力。

**FR-10 为非阻塞删减项**，建议在本 PR 同步清理以降低新增测试维护面，但它本身不是 Request Changes 的决定因素。
