## Part 1/5 — MoE auto-overlap scheduler

### Review baseline

The replacement scheduler still has to preserve the correctness contract of upstream `ep_overlap_schedule_pass`: scheduling must not change tensor semantics; two-chunk regions must be validated; true EP token-exchange markers and their waits must be structurally valid; token-count D2H optimization must only rewrite the validated CPU-copy pattern; and a schedule that cannot be materialized safely must fail rather than silently weaken correctness constraints.

This review also applies the repository's reduction rule: every new scheduler abstraction/state/heuristic is presumed unnecessary unless the behavior cannot be expressed by reusing upstream region metadata/validation or a smaller cost-policy layer.

### Findings

| ID | Severity | Location | Dimension | Problem | Impact | Recommended change |
|---|---|---|---|---|---|---|
| P1-R1 | **BLOCKER** | `npu_moe_auto_scheduler.py:L191-L229, L1252-L1254, L1331-L1332` | Parallel correctness / cross-rank consistency | All agreement uses `torch.distributed.all_gather_object(...)` on the default WORLD group. `run()` checks `if not self.regions: raise` **before** the first WORLD gather. Therefore rank-asymmetric graphs (for example PP stages/local-layer layouts where some ranks have no matching MoE region, or different numbers of regions) can make one rank exit locally while other ranks enter a WORLD collective. Even when every rank participates, every candidate swap performs another Python-object WORLD collective. Communication-order agreement is required only among ranks participating in the relevant communication process group, not across unrelated groups/stages. | This is a compile-time deadlock/unsupported-topology risk, not just overhead. It also globally couples independent EP groups and adds repeated pickle/object-collective host synchronization to every scheduling round. | Remove WORLD-wide agreement from the scheduler. Build/validate a plan **per actual collective PG** and perform consensus only among that PG's members. Do not branch on local region existence before a collective that other ranks may enter. Batch swap scores/eligibility into one deterministic group-local plan (prefer tensor `all_reduce`/small numeric collectives over per-pair `all_gather_object`) and validate the exact benchmark/scheduling manifest for that PG. |
| P1-R2 | **BLOCKER** | `L629-L695`, especially `L652-L661` | Correctness / upstream pass contract / D2H | `_apply_token_count_d2h_protocol()` rewrites four `aten._to_copy` nodes to `non_blocking=[True, True, True, False]`, but its only structural gate is “total copies == 4 and chunk ids contain {0,1}”. It does **not** preserve upstream validations: exactly two sync copies per chunk, CPU destination, copies located in the first token-exchange closure, no stray sync copies, and symmetric presence on both chunks. A 1+3 split or a future non-CPU node carrying the same metadata passes this gate and is rewritten. | This directly changes synchronization semantics. If upstream metadata/layout evolves, the NPU replacement can turn a previously blocking copy asynchronous without proving a later host synchronization dominates every consumer. | Reuse upstream validation instead of recreating a weaker version. Run upstream `ep_overlap_validate_pass` (or factor/expose its validation helper) before NPU scheduling, then apply the NPU cost policy only to a validated region. At minimum restore all upstream D2H checks before mutating `non_blocking`: 2 copies/chunk, CPU destination, first-closure-only, both chunks present, no stray tagged copies. |
| P1-R3 | **BLOCKER** | `L1192-L1242, L1308-L1346` | DAG correctness / upstream pass contract | If the combined regional ordering dependencies form a cycle, `_ordering_deps()` greedily drops individual ordering edges and continues. That is unsafe because some of those “ordering” edges are the only materialization of synthetic correctness constraints introduced by the D2H protocol (copy issue order and final blocking sync before host consumers/data launch). The final checks only validate accepted edges and collective launch order; they do not revalidate D2H dominance or the full selected region order. The code merely logs `skipped_ordering_edges`. | A schedule can compile successfully after silently discarding a correctness-critical synthetic edge. Even when it remains numerically correct, `estimated_hidden_ms/exposed_ms` then describes a schedule that was not actually materialized. This also violates upstream's fail-on-invalid-contract behavior. | Make ordering application all-or-nothing at the region/constraint class level. Separate **mandatory correctness edges** from optional performance preferences; mandatory edges must never be dropped. If a performance schedule conflicts with the full-graph DAG, reject/revert that regional schedule (or keep canonical/upstream order), then re-run postconditions including D2H copy order, final sync domination, wait/launch relationships, and the complete planned phase order. |
| P1-R4 | **HIGH** | `L174-L188, L806-L823, L976-L1003, L1030` | Greedy model correctness / multi-PG communication | The cost simulator keeps one global `inflight` list and `active_remaining = sum(...)` for all recognized collectives, although the file explicitly assigns distinct communication group IDs. `complete_collective_wait()` retires **every earlier launch in the global list** when waiting for one later launch. That implication is only valid for a single ordered queue/stream; it is false across independent process groups/streams. `_estimated_complete_launches()` can then mark unrelated-group launches complete and allow their waits/setup to move. | The greedy score can substantially mis-estimate overlap and can move a wait early based on a false completion assumption, causing unexpected blocking/host stalls. The behavior gets worse if non-EP collectives are admitted into the region. | Either enforce and validate “one schedulable communication PG per MoE region” or model `inflight`, remaining time, retirement, and active windows **per group**. Waiting on launch X may retire only the earlier prefix of X's own queue. Swap/cover calculations must use the relevant queue, not the sum of unrelated groups. |
| P1-R5 | **HIGH** | `L515-L526, L591-L596`; contradicted by `L1312-L1315` | Cross-rank cost alignment | Standalone costs are aligned positionally: only list length is checked, then the median of item `i` is assigned to local node `i`. The same file later states that “FX node IDs, compute nodes, and wait placement may differ under uneven splitting (e.g. DSV4 MHC)”. If two ranks have equal list lengths but different node identities/order, this silently assigns costs from different operators to each other. | The first-round cost model can be corrupted while still passing all checks, driving a poor or unstable communication order. This is especially problematic because the first schedule seeds the fallback costs used by later calibration. | Delete the positional `_align_values()` path and reuse the semantic-key alignment already implemented for whole-graph profiling (or move that logic into one shared helper). Align by stable semantic identity/signature, not list position. If a semantic node is absent on any required rank, leave it unaligned and use an explicit fallback. |
| P1-R6 | **HIGH** | `L826-L868` and `L1131-L1147` | Greedy algorithm / host-bound objective | The PR description says long communication should be filled by **large operators first** to reduce host-bound chains of small launches. The implementation does not do that. It filters by `_FILLER_MIN_COST_MS`, then chooses `min(..., key=original_order)` / `earliest(candidates)`. Thus a 0.06 ms kernel can always beat an independent multi-ms kernel simply because it appeared earlier in the original graph. | The implementation does not guarantee the stated host-bound optimization and can repeatedly issue small kernels while a much better filler is available. | Rank feasible fillers by estimated benefit under the slack budget (for example largest/best-fit compute cost after setup cost, with canonical order only as deterministic tie-break). Keep the safety margin, but make “large-op-first” an actual scoring rule. The same policy should be used for both slack filler and pre-wait filler paths. |
| P1-R7 | **HIGH** | `L64-L76, L235-L262, L362-L395` | Upstream contract / architecture / reduction | The replacement expands the scheduler's semantic domain beyond upstream. `_exchange_label()` treats every c10d functional launch (except wait) as schedulable communication, while `_collect_region_compute_nodes()` pulls previously unowned pure nodes into a region solely by module FQN/direction. Upstream's EP scheduler contract intentionally relies on chunk-body ownership metadata and true annotated token-exchange markers. The NPU extension therefore assumes ownership of unrelated collectives and unowned compute without an explicit semantic marker. | This increases the chance that an upstream GraphTrainer change silently changes what the NPU scheduler moves. It also makes the extension hard to reason about and upgrade: a node can become schedulable just because its FQN happens to lie under the MoE root. | Keep upstream ownership/validation as the correctness layer. Restrict NPU scheduling to `ChunkedRegion` body nodes plus explicitly annotated NPU/EP extension roles (for example token-count/data A2A) rather than “all c10d” and FQN inference. If extra shared work is required as filler, derive it from dependency closure with explicit ownership rules or upstream hooks. This also deletes a large amount of duplicate region-discovery logic. |
| P1-R8 | **MEDIUM** | `L291-L301, L556-L621` | Numerical robustness / cost model | Any exception from the compute benchmark is caught and converted to **0.0 ms**. Custom/profile callbacks are also accepted without checking `isfinite(cost)` or `cost >= 0`. A systemic benchmark/materialization bug therefore looks like free compute, while NaN/Inf/negative values can silently distort queue/slack calculations. | Cost-model failures are hidden and can produce pathological schedules rather than a clear unsupported-node/fallback path. Zero is particularly unsafe because it classifies real compute as plumbing. | Validate every measured cost once at the boundary: finite and non-negative. Distinguish “unsupported node” from benchmark/runtime failure. For unsupported nodes use an explicit prior/heuristic fallback; for systemic benchmark failures fail the scheduling round or retain canonical/upstream order instead of silently assigning zero. |
| P1-R9 | **MEDIUM** | `L929-L948` plus repeated scans in `_select_next_launch`, `_select_slack_filler`, and the main loop | Memory / compile-time host bound / reduction | For every region, the scheduler materializes a transitive `set[Node]` ancestor closure for **every graph node**, then creates transitive successor relationships for region nodes. The greedy loop repeatedly scans all region nodes. This work is repeated for the standalone round and every calibration round. Worst-case memory/time scales roughly with full-graph-size × region-size per region, plus quadratic region scans. | Large DeepSeek graphs can pay significant Python set allocation/hash overhead and compile-time memory pressure before training starts; the design scales poorly with number of MoE layers and calibration rounds. | Reuse upstream body/closure utilities and keep only direct local dependencies in the ready DAG. Compute reachability on demand with memoization/bitsets where needed for cross-boundary checks. Maintain indexed ready/filler candidate sets instead of rescanning all nodes each decision. This is also a substantial code-size reduction opportunity. |
| P1-R10 | **INFO / maintainability** | `L264-L288, L486-L512` interacting with `compute_benchmark.py` | GMM maintainer comment / cost-model ownership | The GitCode question “why does GMM need special handling?” is valid to ask, but the special materialization itself is justified: `aten._grouped_mm` consumes value-sensitive cumulative expert offsets and may have a symbolic routed-token dimension. Generic random tensor materialization can generate illegal offsets; the benchmark therefore needs a balanced legal `offs` vector and an assumed routed-token count. The issue is that the scheduler now knows `_GROUPED_MM_TARGET`, permutation target sets, and their materialization assumptions. | Keeping the GMM behavior is necessary, but target-specific benchmark policy in the scheduler increases coupling and duplicates knowledge owned by `ComputeBenchmarker`. | **Do not remove the GMM-specific benchmark semantics.** Instead move “can benchmark / required routing assumption / assumption construction” behind the benchmark layer, so the scheduler asks for a cost with region routing metadata and does not branch on private target strings. This addresses the maintainer comment while reducing scheduler code and upgrade surface. |

### Additional observations

| Area | Result |
|---|---|
| Dependency safety inside one local region | The projected-ancestor approach correctly notices dependencies that leave and re-enter the region, but its correctness is weakened by the later “drop conflicting ordering edge and continue” fallback (P1-R3). |
| Communication swap agreement | The code correctly avoids making a local-only branch before the swap vote and includes local eligibility in consensus; however the consensus scope is wrong (WORLD rather than the actual PG), which is the larger issue in P1-R1. |
| Count/D2H intent | Pairing four token-count copies into one final host sync matches the upstream optimization intent, but this replacement omits the upstream structural validation required before changing blocking semantics (P1-R2). |
| Greedy long-communication fill | Slack reservation exists, but candidate ranking does not implement the advertised “large op first” behavior (P1-R6). |
| Whole-graph calibration interaction | Reusing profile costs by stable node ID is directionally sound; the first standalone round's positional cross-rank alignment is the inconsistent weak link (P1-R5). |
| GMM benchmark | Special handling is necessary for legal offsets/dynamic routed rows; ownership of that policy should move out of the scheduler (P1-R10). |
| Upstream decoupling | This 1356-line scheduler reimplements region ownership, exchange/wait pairing, D2H rewrite, dependency planning and topological ordering that upstream already treats as its scheduler correctness layer. The preferred architecture is “upstream validation/region semantics + thin NPU cost policy”, not a second independent scheduler contract. |

### Part 1 conclusion

**Changes required before this scheduler is acceptable.** P1-R1/P1-R2/P1-R3 are correctness/topology blockers. P1-R4/P1-R5/P1-R6/P1-R7 materially affect the claimed auto-scheduling behavior and upstream-decoupling goal. The GMM special case itself is justified; its placement/API should be simplified rather than removed.
