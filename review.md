## Part 1/4 conclusion

**Request Changes.** The Holt level/trend recurrence itself is sound, but the detector currently has two state-machine correctness problems that can materially change rollback behavior: the anomaly-statistics freeze restarts forever after every lookback window, and cooldown is keyed to a training step that moves backwards after rollback. There are also numerical-stability and configuration-boundary gaps that should be closed before enabling automatic rollback.

Severity used below: **S1** = correctness/blocking; **S2** = important robustness/architecture issue; **S3** = cleanup/non-blocking.

| ID | Severity | Code location | Problem | Why it matters | Suggested change |
|---|---|---|---|---|---|
| P1-R1 | S1 | `detector.py:162-175` | The bounded statistics freeze does not actually become “accept the new normal after `onset_lookback`”. When `_frozen_steps == onset_lookback`, one anomalous sample is incorporated, then line 175 resets `_frozen_steps = 0`; if the next sample is still above `onset_z_threshold`, the detector freezes for another full window. A sustained 2–6σ regime therefore updates the Holt state only once every `onset_lookback + 1` observations instead of resuming normal adaptation after the bounded hold. | This directly contradicts the docstring at lines 168-170 and can leave the baseline stale for hundreds/thousands of steps. A persistent but non-triggering regime change can later be misclassified as a spike because the detector keeps re-entering the same freeze window. Example with `onset_lookback=64`: observations 1-64 above the onset threshold are frozen, 65 is accepted, 66-129 are frozen again. | Fix without adding another abstraction/state object: saturate `_frozen_steps` at `onset_lookback`. While anomalous and below the limit, freeze and increment; once the limit is reached, keep the counter saturated and update every subsequent anomalous observation. Reset it to 0 only after an observation falls back to/below the onset threshold (or on detector reset). Add a focused regression for a sustained 2–6σ level shift. |
| P1-R2 | S1 | `detector.py:93, 96-108, 140-147` | Cooldown is measured from `_last_trigger_step`, but the supplied `step` is the trainer step and therefore moves backwards after rollback. `reset()` deliberately preserves `_last_trigger_step`. After a trigger at step 1000 and rollback to step 900, the next trigger is not allowed until `step > 1500`; the effective cooldown has silently grown by the rollback distance. A farther rollback can suppress detection for most or all of the remaining run. | The configured `cooldown_steps` no longer means a stable number of executed training steps between triggers. This is especially dangerous for an automatic recovery feature because the first rollback can disable later protection for an unexpectedly long interval. | Base cooldown on a monotonic clock that does not rewind with checkpoint restore, or explicitly rebase the stored trigger point when rollback changes the model step. Keep the implementation minimal; the important invariant is that rollback distance must not be added to cooldown implicitly. Add a regression where trigger step > rollback target and verify the next eligible trigger after exactly the intended cooldown. |
| P1-R3 | S2 | `detector.py:116-118, 135-136, 187-191` | Standardization has no statistically meaningful variance floor: `z = residual / (sigma + 1e-12)`. After a perfectly/near-stable warmup, `sigma` can be zero or tiny, so a numerically negligible loss change becomes an enormous z-score. For example, 100 observations of loss `1.0` leave `sigma == 0`; the next loss `1.0 + 1e-9` yields `z ≈ 1000` and triggers with the default threshold 6. Separately, a finite but huge residual can overflow `residual * residual` to `inf`, after which `sigma=inf` makes the detector effectively blind. | False positive rollback is much more expensive than an ordinary metric spike, and poisoned `_var` can silently disable detection for the rest of the run. The fixed `1e-12` denominator is not scale-aware. | Do not add a new CLI knob unless there is a real tuning requirement. Prefer deriving a safe floor from the observed/predicted loss scale or defer z-scoring until a non-degenerate residual scale is established. Also fail/reset explicitly if the derived residual/variance state becomes non-finite instead of letting `inf` propagate. Add constant-loss and extreme-finite-value tests. |
| P1-R4 | S2 | `detector.py:69-88` | `z_threshold` and `onset_z_threshold` do not reject NaN/Inf. Comparisons such as `nan <= 0` and `nan > z_threshold` are both false, so NaN passes validation. `z_threshold=inf` silently disables triggering; `onset_z_threshold=nan` makes the reverse onset walk never hit its break condition and can report the oldest retained record regardless of its z-score. | These are CLI-visible float fields; Python/tyro can represent non-finite floats. A malformed value should fail configuration deterministically, not silently mutate detector semantics. | Validate all float detector parameters with `math.isfinite` before range checks. The existing range checks for the decay values already reject NaN/Inf indirectly, but an explicit finite check for all four float parameters is clearer and avoids asymmetric behavior. |
| P1-R5 | S2 | `config.py` ownership; verified via `trainer.py:55-68` and current `engine.py:30-44` | The existing maintainer concern (“`validate_config` 放在 `_post_init_optimizer` 里面是否合适”) is only **partially resolved** on the current mirror head. The call is now correctly outside `_post_init_optimizer()`, at the end of `TrainerEx.Config.__post_init__()`; that call site is appropriate because the validation spans `anticipatory`, `checkpoint`, `debug`, and optional EMA config, and upstream `Trainer.Config.__post_init__` already owns cross-field config validation. However, contrary to the PR-side note that the implementation was moved to `config.py`, head `a8004a9` still defines `validate_anticipatory_config` in `engine.py:30-44`, and `trainer.py` imports it from there. | Config construction should not depend on the runtime recovery engine module. Keeping validation in `engine.py` mixes schema policy with runtime/checkpoint machinery and makes the architecture harder to keep decoupled as upstream changes. It also means the stated refactor is not actually present in the reviewed head. | Keep the current call site in `TrainerEx.Config.__post_init__`, but move the validator (and only the constants it needs) into `anticipatory_routing/config.py`. Do not move it back into `_post_init_optimizer`; optimizer materialization and anticipatory cross-config validation are separate concerns. |
| P1-R6 | S2 | `config.py:40-42` plus cross-validator behavior verified at current `engine.py:31-36` | `max_rollbacks=0` is explicitly accepted and documented as “do not execute rollback”, but `validate_anticipatory_config` still requires checkpoint saving whenever `anticipatory.enable=True`. Thus the documented no-rollback/detection-only configuration `--anticipatory.enable --anticipatory.max-rollbacks 0` is rejected unless checkpointing is enabled, even though no rollback can occur. | This is a configuration semantic mismatch: either `0` is a supported independent user meaning or it should not be exposed/documented as such. Requiring unrelated checkpoint state for a mode that cannot consume it violates the “single simple CLI semantics” requirement. | Prefer the smaller behavior change: if `max_rollbacks == 0`, skip rollback-specific checkpoint compatibility validation (while retaining any checks still needed for detector/router operation). Alternatively, if detection-only mode is not a real supported product semantic, reject `max_rollbacks=0` and remove the documentation claiming otherwise. Do not keep the current ambiguous middle state. |

## Verified / no additional issue in this segment

- `detector.py:189-190`: the Holt level/trend update is structurally correct with `alpha = 1 - level_decay` and `beta = 1 - trend_decay`; no extra Holt helper/class should be introduced.
- `detector.py:141-146`: given a valid recent z-score history, the reverse walk correctly finds the earliest member of the contiguous run with `z > onset_z_threshold`; the issues above are with history/statistics lifecycle, not this loop itself.
- `config.py:50-56`: the basic integer range checks for `delay_steps`, `active_steps`, and `max_rollbacks` match the documented meanings.
- The nested `LossSpikeDetector.Config` is justified because it is a real CLI/configurable component and `Configurable.Config.build()` is reused; no additional detector factory/wrapper is needed.
- `__init__.py`: no issue. It is a minimal package marker/docstring, exports no redundant API, and the location under `extensions/experiment/anticipatory_routing` is consistent with the repository's Extensions/experiment organization.

### Part 2/4 conclusion

**Request Changes.** The NORMAL → rollback/WARMUP → ACTIVE → DRAIN → NORMAL queue arithmetic is internally coherent for the non-PP path, and the two earlier maintainer concerns about step-level detection and iterator reset are addressed. The remaining blockers are mostly at integration boundaries: Pipeline Parallel is not actually supported but is not rejected; rollback does not restore the checkpoint-time stochastic state; the rollback happens inside `train_step()` while upstream `train()` still executes its post-step tail; and checkpoint “completeness” validation is weaker than the PR description claims.

| ID | Severity | Code location | Problem | Why it matters | Suggested change |
|---|---|---|---|---|---|
| P2-R1 | S1 | `schedule.py:73-112, 145, 177-183, 301-338`; `engine.py:89-99, 139-146` | Pipeline Parallelism is silently admitted, but the schedule is structurally non-PP. `_microbatches_per_step` is only `gradient_accumulation_steps`, while upstream v0.3.0 consumes `gradient_accumulation_steps * num_pipeline_parallel_microbatches`. `SuppliedMicrobatches` will therefore under-supply the base `train_step`. Add one explicit compatibility check that rejects `parallelism.pipeline_parallel_degree > 1` when anticipatory routing is enabled, with a clear error. Remove any docs/tests implying PP support. ### Verified / no additional issue in this segment

- The basic queue arithmetic for non-PP execution is coherent: WARMUP fills up to `delay_steps`; ACTIVE prefetches one step then pops one; DRAIN stops prefetch and consumes the remainder; the queue is bounded to approximately `delay_steps + 1` step objects at the transient ACTIVE prefetch peak.
- Checkpoint saving is correctly suppressed while prefetched data makes the dataloader cursor lead the parameter step, and it resumes only after the queue drains. If an in-step exception occurs, `engine.failed` also prevents a later accidental save.
- `_isolated_forward()` restores registered buffers, `LoggedAuxLoss` accumulators, `ntokens_seen`, Python/NumPy RNG, and the torch device RNG via `fork_rng`, and resets FSDP iteration state in a `finally` block. I did not find a missing restore on the forward-only path itself.
- `rollback_to()` waits for pending checkpoint work and outstanding EMA parameter reads before DCP load; persistent model buffers are restored through model state, gradients/transient MoE and aux-loss counters are reset after load, and the resumable data wrapper is rebuilt from the restored dataloader state.
- Rank-0 checkpoint selection followed by a broadcast gives all ranks the same target in the non-PP path; unreadable metadata is skipped before the target is broadcast.
