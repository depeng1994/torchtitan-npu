## Part 1/4 conclusion

**Request Changes.** The Holt level/trend recurrence itself is sound, but the detector currently has two state-machine correctness problems that can materially change rollback behavior: the anomaly-statistics freeze restarts forever after every lookback window, and cooldown is keyed to a training step that moves backwards after rollback. There are also numerical-stability and configuration-boundary gaps that should be closed before enabling automatic rollback.

Severity used below: **S1** = correctness/blocking; **S2** = important robustness/architecture issue; **S3** = cleanup/non-blocking.

| ID | Severity | Code location | Problem | Why it matters | Suggested change |
|---|---|---|---|---|---|
| P1-R1 | S1 | `detector.py:162-175` | The bounded statistics freeze does not actually become “accept the new normal after `onset_lookback`”. When `_frozen_steps == onset_lookback`, one anomalous sample is incorporated, then line 175 resets `_frozen_steps = 0`; if the next sample is still above `onset_z_threshold`, the detector freezes for another full window. A sustained 2–6σ regime therefore updates the Holt state only once every `onset_lookback + 1` observations instead of resuming normal adaptation after the bounded hold. | This directly contradicts the docstring at lines 168-170 and can leave the baseline stale for hundreds/thousands of steps. A persistent but non-triggering regime change can later be misclassified as a spike because the detector keeps re-entering the same freeze window. Example with `onset_lookback=64`: observations 1-64 above the onset threshold are frozen, 65 is accepted, 66-129 are frozen again. | Fix without adding another abstraction/state object: saturate `_frozen_steps` at `onset_lookback`. While anomalous and below the limit, freeze and increment; once the limit is reached, keep the counter saturated and update every subsequent anomalous observation. Reset it to 0 only after an observation falls back to/below the onset threshold (or on detector reset). Add a focused regression for a sustained 2–6σ level shift. |
| P1-R2 | S1 | `detector.py:93, 96-108, 140-147` | Cooldown is measured from `_last_trigger_step`, but the supplied `step` is the trainer step and therefore moves backwards after rollback. `reset()` deliberately preserves `_last_trigger_step`. ### Part 2/4 conclusion

**Request Changes.** The NORMAL → rollback/WARMUP → ACTIVE → DRAIN → NORMAL queue arithmetic is internally coherent for the non-PP path, and the two earlier maintainer concerns about step-level detection and iterator reset are addressed. The remaining blockers are mostly at integration boundaries: Pipeline Parallel is not actually supported but is not rejected; rollback does not restore the checkpoint-time stochastic state; the rollback happens inside `train_step()` while upstream `train()` still executes its post-step tail; and checkpoint “completeness” validation is weaker than the PR description claims.

### Verified / no additional issue in this segment

- The basic queue arithmetic for non-PP execution is coherent: WARMUP fills up to `delay_steps`; ACTIVE prefetches one step then pops one; DRAIN stops prefetch and consumes the remainder; the queue is bounded to approximately `delay_steps + 1` step objects at the transient ACTIVE prefetch peak.
- Checkpoint saving is correctly suppressed while prefetched data makes the dataloader cursor lead the parameter step, and it resumes only after the queue drains. If an in-step exception occurs, `engine.failed` also prevents a later accidental save.
- `_isolated_forward()` restores registered buffers, `LoggedAuxLoss` accumulators, `ntokens_seen`, Python/NumPy RNG, and the torch device RNG via `fork_rng`, and resets FSDP iteration state in a `finally` block. I did not find a missing restore on the forward-only path itself.
- `rollback_to()` waits for pending checkpoint work and outstanding EMA parameter reads before DCP load; persistent model buffers are restored through model state, gradients/transient MoE and aux-loss counters are reset after load, and the resumable data wrapper is rebuilt from the restored dataloader state.
- Rank-0 checkpoint selection followed by a broadcast gives all ranks the same target in the non-PP path; unreadable metadata is skipped before the target is broadcast.

### Part 3/4 conclusion

**Request Changes.** The core replay math is correct: the cached object is only the discrete expert ID; `HashRouter.forward` still computes current gate scores and gathers the selected scores from the current forward, so score/gate gradients are not replayed. ### Router / cache correctness verified

- **Current-score gradient is preserved.** `AnticipatoryHashRouter._select_experts()` changes only the discrete IDs. In the existing NPU `HashRouter.forward`, gate scores are recomputed from the current input/parameters, the cached IDs are used by `scores.gather(...)`, route normalization/scale then operate on those current scores, and autograd therefore reaches the current gate parameters. The cached ID tensor itself is intentionally non-differentiable.
- **Compression does not change the selected IDs** for representable expert counts: capture detaches and casts the non-negative IDs to the configured signed integer storage type; replay converts/copies them back to int64 before `gather`.
- **Hash routers are correctly excluded from replay** when mixed with dynamic routers: `hash=True` keeps the original `HashRouter.Config`, and that forward path uses its fixed `tid2eid` table rather than `_select_experts`.
